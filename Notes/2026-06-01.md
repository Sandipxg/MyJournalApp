# Node.js Backend Revision - 2026-06-01

Today we learned and implemented two important backend concepts in our journal app:

1. Controllers
2. Middleware and global error handling

## 1. Old Backend Flow

Before today's changes, the backend flow was:

```txt
server.js
  -> routes
  -> services
  -> JSON database files
```

The route files were doing too many things:

- Defining API URLs
- Reading request data
- Validating input
- Calling service functions
- Sending responses
- Handling errors with `try/catch`

Example:

```js
router.post('/login', (req, res) => {
  const { username, password } = req.body

  try {
    const user = authService.login(username, password)
    res.json(user)
  } catch (err) {
    res.status(401).json({ error: err.message })
  }
})
```

This works, but as the app grows, route files become messy.

## 2. Controller Concept

A controller is responsible for handling request and response logic.

After adding controllers, the flow became:

```txt
server.js
  -> routes
  -> controllers
  -> services
  -> JSON database files
```

The route file now only maps a URL to a controller function.

Example:

```js
router.post('/login', authController.login)
```

The controller handles:

- `req.body`
- `req.params`
- `req.query`
- Basic validation
- Sending success responses

Example:

```js
function login(req, res) {
  const { username, password } = req.body

  if (!username || !password) {
    throw new AppError('username and password required', 400)
  }

  const user = authService.login(username, password)
  res.json(user)
}
```

The service still handles the actual business logic.

Example:

```js
function login(username, password) {
  const users = readUsers()
  const user = users.find(u => u.username === username && u.password === password)

  if (!user) {
    throw new AppError('Invalid username or password', 401)
  }

  return { id: user.id, username: user.username }
}
```

## 3. Route vs Controller vs Service

Simple meaning:

```txt
Route = Which URL should call which function?
Controller = How should request and response be handled?
Service = What is the actual app logic?
```

Example:

```txt
POST /api/auth/login
  -> auth route
  -> authController.login
  -> authService.login
  -> users.json
```

## 4. Middleware Concept

Middleware is just a function.

What makes it special is that Express places it in the request flow.

Normal middleware looks like this:

```js
function middleware(req, res, next) {
  next()
}
```

Middleware can:

- Read the request
- Modify the request
- Send a response
- Call `next()` to continue

Example:

```js
app.use(express.json())
```

This middleware reads JSON request bodies and makes them available as:

```js
req.body
```

Without `express.json()`, this code may not work correctly:

```js
const { username, password } = req.body
```

## 5. Middleware Order

Middleware runs from top to bottom.

Our `server.js` now has this flow:

```js
app.use(cors({ origin: 'http://localhost:5173' }))
app.use(express.json())

app.use('/api/auth', authRoutes)
app.use('/api/journals', journalRoutes)

app.use(notFound)
app.use(errorHandler)
```

For a login request:

```txt
POST /api/auth/login
  -> cors middleware
  -> express.json middleware
  -> authRoutes
  -> authController.login
  -> authService.login
  -> response
```

For an unknown request:

```txt
GET /api/random
  -> cors middleware
  -> express.json middleware
  -> authRoutes does not match
  -> journalRoutes does not match
  -> notFound middleware sends 404
```

## 6. What Is `next()`?

`next()` means:

```txt
I am done. Go to the next middleware or route.
```

Example:

```js
function logger(req, res, next) {
  console.log(req.method, req.url)
  next()
}
```

If a middleware does not send a response and does not call `next()`, the request gets stuck.

## 7. Error Middleware

Normal middleware has 3 parameters:

```js
function middleware(req, res, next) {}
```

Error middleware has 4 parameters:

```js
function errorHandler(err, req, res, next) {}
```

The first parameter, `err`, makes it special.

Express understands:

```txt
This middleware is for handling errors.
```

Our error handler:

```js
function errorHandler(err, req, res, next) {
  const statusCode = err.statusCode || 500
  const message = err.message || 'Something went wrong'

  res.status(statusCode).json({ error: message })
}
```

This means:

- If the error has a status code, use it
- Otherwise use `500`
- If the error has a message, send it
- Otherwise send `Something went wrong`

## 8. AppError

Normal JavaScript errors only have a message:

```js
throw new Error('Journal not found')
```

But for APIs, we also need an HTTP status code.

So we created `AppError`:

```js
class AppError extends Error {
  constructor(message, statusCode) {
    super(message)
    this.statusCode = statusCode
  }
}
```

Now we can throw errors like this:

```js
throw new AppError('Journal not found', 404)
```

This error contains:

```txt
message: Journal not found
statusCode: 404
```

Then `errorHandler` sends the correct response.

## 9. Global Error Handling Flow

Example: user opens a journal that does not exist.

```txt
GET /api/journals/999
  -> journal route
  -> journalController.getById
  -> journalService.getById
  -> service throws AppError('Journal not found', 404)
  -> errorHandler catches it
  -> response: { error: 'Journal not found' }
```

This removes repeated `try/catch` blocks from controllers.

Before:

```js
try {
  res.json(journalService.getById(id))
} catch (err) {
  res.status(404).json({ error: err.message })
}
```

After:

```js
res.json(journalService.getById(id))
```

If the service throws an `AppError`, the global error handler handles it.

## 10. Final Mental Model

Think of the backend flow like this:

```txt
Request
  -> middleware
  -> route
  -> controller
  -> service
  -> database/file
  -> response
```

If something goes wrong:

```txt
service/controller throws AppError
  -> errorHandler
  -> error response
```

## Key Takeaways

- Middleware is just a function used inside Express's request flow.
- Middleware runs in the order it is registered.
- `next()` moves the request to the next middleware.
- Routes should only map URLs to controller functions.
- Controllers should handle request and response.
- Services should contain the actual logic.
- `AppError` helps send errors with proper status codes.
- `errorHandler` keeps error responses in one common place.
